# Contract build

The contract build is the only place documentation is produced. It evaluates the whole module
tree, the response traits and the explicit declarations, then writes the two committed artifacts.
This page covers the build entry points, the artifact shape, versioning and the CLI.

## Build pipeline

```text
src/lib.rs + api! + routes! + #[handler] + #[roundhouse::schema]
        │
        ├─ build.rs                              generated by `cargo roundhouse init`/`new`
        │     calls roundhouse_build::prepare() before rustc reads include_contract!
        │
        ├─ prepare: analyze src                   -> target/roundhouse/handlers.json
        │     opaque return sites only; named types need no index
        │
        ├─ target/roundhouse/harness             generated per prepare/check
        │     compiles the app with ROUNDHOUSE_HANDLER_INDEX
        │     calls <crate>::__roundhouse_contract() from api!
        │
        ▼
  .roundhouse/contract.json      runtime: operations, plans, response table, $defs
  .roundhouse/openapi.json       documentation: OpenAPI 3.1
```

A `build.rs` should contain:

```rust
fn main() {
    println!("cargo:rerun-if-changed=src");
    println!("cargo:rerun-if-changed=Cargo.toml");
    println!("cargo:rerun-if-changed=Cargo.lock");
    if std::env::var_os("ROUNDHOUSE_BUILDING_CONTRACT").is_some() {
        return;
    }
    roundhouse_build::prepare().expect("roundhouse contract generation failed");
}
```

The generated script additionally handles the CI and opt-in behaviour described below.
`roundhouse_build::prepare()` writes `.roundhouse/`; `prepare_to(path)` writes the same artifacts
elsewhere. `ARTIFACT_DIR` is `.roundhouse`.

`prepare` first runs the handler analyzer over the application library and writes
`target/roundhouse/handlers.json`. It then creates the harness under `target/roundhouse`, with the
application crate as a dependency and `roundhouse` with the `contract` feature. Feature unification
makes the application's `api!` block visible for that build only. The harness target directory is
`target/roundhouse`; nothing outside `target/` and `.roundhouse/` is written. There is no generated
`src/bin` file and no generated feature.

The analyzer only selects the concrete type at an opaque handler's tail and `return` sites. It
never decides a status or schema; `DocumentedResponse` / `DocumentedError` own those. `#[handler]`
reads the index when `ROUNDHOUSE_HANDLER_INDEX` is set and emits typed trait calls, so a wrong
selection is a compiler error. Named return types are documented without the index.

The application's build script depends on `roundhouse-build`; `cargo roundhouse init` installs it
and writes the build script. A hand-written build script only needs the two-line call and the
build-dependency.

## Build modes

| Mode | Who runs it | What it does |
|---|---|---|
| Automatic | generated `build.rs` | Calls `roundhouse_build::prepare()` when source, manifest or lockfile inputs change. |
| Explicit | `cargo roundhouse prepare` | The same generation on demand. |
| Verify | `cargo roundhouse check` | Regenerates into `target/roundhouse-check-<pid>` and compares the committed files. |

The build script and the CLI share `roundhouse-build`, so there is one generator implementation.
The harness run sets `ROUNDHOUSE_BUILDING_CONTRACT`, so the application's build script does not
recurse. The generated script also returns early when `ROUNDHOUSE_AUTO_CONTRACT=0`, and in CI when
`CI` is set and `ROUNDHOUSE_AUTO_CONTRACT` is unset. That keeps `cargo roundhouse check`
meaningful: CI builds the committed artifact and the check detects drift. Set
`ROUNDHOUSE_AUTO_CONTRACT=1` to opt back into automatic generation in CI.

There is one build, and it is strict. A handler with no documented success response fails
`prepare`; the error points to the handler. There is no discovery pass and no status/schema
inference: the analyzer names a type, and the traits describe it.

## Artifact shape

`contract.json` starts with:

```json
{
  "kind": "roundhouse.contract",
  "contract_version": 1,
  "generator_version": "0.4.0",
  "openapi": "openapi.json"
}
```

It also contains:

- **`operations`** — one object per route with `operation_id`, `handler`, `method`, `path`,
  `module`, `source` location, `tags`, `deprecated`, `hidden`, `security`, the validation policy
  (`schema`, `parts` or `off`), the request body and the response table. A response is the type's
  documented response, an extractor or layer response, or an explicit declaration; there is no
  inferred provenance.
- **`validation.defs`** — the shared component schemas, expressed as `#/$defs/..`.
- **`validation.bodies.ops`** — request body plans keyed by operation id, with content type and
  schema.
- **`validation.bodies.types`** — body schemas keyed by stable type name, also usable by
  extractors that enforce their own schema.
- **`validation.parts.types`** — path/query/form schemas keyed by stable type name.
- **`diagnostics`** — non-fatal observations collected during the build.

`openapi.json` is the OpenAPI 3.1 projection of the same build. It is what the runtime serves.
`Built::openapi_30()` / `Built::openapi_30_json()` produce a best-effort 3.0.3 shape for tools
that require it.

Body plans are keyed by operation id plus stable type name; parts plans are keyed by stable type
name. The runtime engine never looks up a plan by `TypeId`.

## Contract versioning

`contract_version` is the compatibility contract. This runtime accepts only version `1` and fails
`App::build` with `BuildError::InvalidContract` otherwise. A breaking layout change bumps the
version and requires rerunning `cargo roundhouse prepare`. `generator_version` is informational;
it does not gate loading.

## CLI

`roundhouse-build` is the generator library used by `build.rs`. `roundhouse-cli` is the
`cargo-roundhouse` binary and owns `init` plus the developer/CI commands.

```sh
cargo roundhouse init [path] [--name <name>] [--no-build-script]
cargo roundhouse new <path> [--name <name>] [--no-build-script]
cargo roundhouse prepare [--out <directory>]
cargo roundhouse check
cargo roundhouse explain <operation-id | path | "METHOD /path">
cargo roundhouse verify [-- <cargo test args>...]
cargo roundhouse diff [--against <contract.json>] [--check]
```

- **`init`** follows Cargo's `init` convention: it initializes a package in the current directory
  (or `path`), running `cargo init --lib` when there is no manifest. **`new`** follows `cargo new`:
  it creates `path` first. A new package gets a library target (`src/lib.rs`), a thin
  `src/main.rs`, `.roundhouse/`, the runtime dependencies and the test-only contract dependency.
- **Adopting an existing package** adds `.roundhouse/` and, unless `--no-build-script` is
  passed, the `roundhouse-build` build-dependency and a guarded `build.rs`; it also prints the
  `api!` snippet. Existing sources and runtime dependencies are left alone. An existing hand-written
  `build.rs` is never overwritten; the roundhouse block is printed for manual insertion. An
  existing package without a library target is refused with the library guidance.
- **Contract builds seed missing artifacts.** Before the harness compiles the application,
  `prepare` writes empty, valid `contract.json`/`openapi.json` when they do not exist. This lets
  `include_contract!` compile on a clean checkout; the real artifacts replace the placeholders
  after the build succeeds.
- **`prepare`** runs the harness and reports how many operations were written. `--out` chooses
  another artifact directory.
- **`check`** requires both committed artifacts, regenerates them into
  `target/roundhouse-check-<pid>` and compares the parsed JSON. It fails if either file is stale.
- **`explain`** reads the committed `contract.json` and prints one operation's method, path,
  source location, and each response's status, content type, schema ref and description.
- **`verify`** runs `cargo test` with `ROUNDHOUSE_VERIFY=1`, enabling response verification
  without changing application code. It requires a committed contract.
- **`diff`** compares the committed contract with `git HEAD` or `--against`. Removed operations,
  responses and content types, operation-id changes, added or changed request bodies, and security
  changes are breaking; additions are compatible. `--check` exits non-zero when a breaking change
  is found.

`cargo build` and `cargo test` refresh `.roundhouse/` automatically through the generated build
script before `include_contract!` expands. `cargo roundhouse prepare` remains available for an
explicit run; `cargo roundhouse check` is the CI gate.

## Failure model

The contract build is strict by default. `App::permissive()` downgrades diagnostics to warnings
and publishes a marked `default` placeholder for a missing success;
`Contract::permissive()` downgrades diagnostics without supplying that placeholder. Strict builds
reject an undeclared success.

`Contract::register::<T>()` (and `api! register = [T]`) publishes a private body or response type
the harness cannot see through an extractor or return type. It is the explicit escape hatch for
visibility, not for inference.

The CLI writes only `.roundhouse/` and temporary directories under `target/`. The application's
`src/` and `Cargo.toml` are untouched after `init`.
