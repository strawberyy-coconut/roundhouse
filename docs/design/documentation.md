# Documentation

The router and the OpenAPI document come from the same declarations. There is no side-car
specification and no second description to keep in sync:

- `routes!` supplies each operation's path, method, tags, layers, security and route policy.
- `#[handler]` supplies the request, response and security contribution derived from the
  signature, plus prose tags and explicit response declarations.
- `#[roundhouse::schema]` supplies the body shape and the runtime validation hooks.
- `prepare` turns those contributions into the committed OpenAPI document.

In 0.4 the document is generated by the build, not by the running server. Production serves
`.roundhouse/openapi.json` verbatim. See [Contract](contract.md) for the build pipeline.

## From declaration to operation

```text
#[handler] async fn show(Path(id): Path<NoteId>) -> Result<Json<Note>, Problem>
    │
    ├─ marker type: HandlerSpec (state, captures, required auth) + DocSource (operation)
    ├─ generated shim: extractors + ValidationContext + route policy
    │
    └─ contract build calls DocSource::operation(&mut DocContext)
            │
            ▼
        OperationDoc
            ├─ doc tags and typed response declarations
            ├─ the return type's DocumentedResponse impl
            ├─ argument contributions from ExtractDoc
            ├─ route policy (body validation, auth)
            └─ entry-level `doc = |docs|` hook
            │
            ▼
        doc::build
            ├─ align captures with parameters
            ├─ merge layer docs, guards, rejections and documented responses
            ├─ apply response prose and `response_defaults`
            ├─ validate the operation's success and security
            └─ validate_document
            │
            ▼
        OpenApi 3.1 → .roundhouse/openapi.json
```

`OperationDoc` is data. The macro emits the code that fills it; the contract builder owns every
merge rule. Response documentation is not a separate input: the return type's
`DocumentedResponse` impl supplies it directly, and an explicit declaration supplies whatever the
type cannot name.

## `#[handler]`, `HandlerSpec` and `DocSource`

The attribute leaves the handler untouched and emits a hidden marker type beside it. The marker
implements two traits:

```rust
pub trait HandlerSpec: Send + Sync + 'static {
    type State: 'static;
    const HAS_STATE: bool;
    const PATH_NAMES: &'static [&'static str] = &[];
    const REQUIRED_AUTH: &'static [&'static str] = &[];
}

pub trait DocSource {
    fn operation(context: &mut DocContext<'_>) -> OperationDoc;
}
```

| Item | Source |
|---|---|
| `State` / `HAS_STATE` | `State<T>` in the signature, or `()` |
| `PATH_NAMES` | `Path<T>` where `T: Params` |
| `REQUIRED_AUTH` | `Auth<A>` (not `Option<Auth<A>>`) |
| `operation(..)` | Doc tags, one contribution per argument, response statements |

`routes!` registers a generated shim (`__roundhouse_shim::<P>`), not the function. The shim has
the handler's extractors plus a `ValidationContext` and the route policy's auth extractor; it
validates after extraction and then calls the handler. The marker type is what lets `routes!`
find the metadata without re-parsing the function.

The marker type is also the missing-attribute diagnostic: `routes!` aliases it before use, so a
plain `async fn` produces one "type not found" error pointing at the missing `#[handler]` instead
of a cascade of module-path errors.

Only the signature is read by the macro. Response structure comes from the contract build and its
source analyzer, not from parsing the function inside the proc macro.

## Extractors: `ExtractArg` and `ExtractDoc`

Extraction and documentation are separate traits, so production compiles only what it runs:

```rust
pub trait ExtractArg {
    const IS_BODY: bool = false;
    const SHIM_VALIDATES: bool = false;

    fn validate(&self, context: &ValidationContext) -> Result<(), Problem> {
        Ok(())
    }
}

#[cfg(feature = "contract")]
pub trait ExtractDoc: ExtractArg {
    fn document(context: &mut DocContext<'_>) -> ArgDoc;
}
```

- `validate` runs after extraction. The default is a no-op for extractors that already enforce
  their own contract.
- `IS_BODY` keeps the one-body rule and the validation marker honest.
- `SHIM_VALIDATES` says the extractor already executed the schema, so the shim does not run it a
  second time.
- `document` returns an `ArgDoc`; it does not mutate a shared bag. The builder owns the merge
  rules.

`Option<Self>` and `Result<Self, E>` are wrapper impls. `Option` relaxes parameters, the body and
required auth into their optional form. `Result` drops extractor failure responses because the
handler owns the rejection.

`Json<T>`, `Form<T>`, `Path<T>`, `Query<T>`, `RepeatedQuery<T>`, `Extension<T>`, `State<T>`,
`Bytes`, `Body`, `Auth<A>`, `Strict<..>`, `Mapped<..>` and the no-op axum parts extractors have
implementations. A custom extractor implements `ExtractArg` and, under `contract`, `ExtractDoc`.
See [Extensibility](extensibility.md).

### The concrete-type probe

The macro sees only the token `T` of an argument. It cannot ask "does `T` implement `ExtractDoc`?"
with a normal bound, because a foreign extractor without an impl must still compile. The probe
uses autoref specialization:

```rust
impl<T: ExtractDoc> ProbeArg<T> for &ArgProbe<T> { /* the real documentation */ }
impl<T>             ProbeArg<T> for &&ArgProbe<T> { /* mark unverified */ }
```

The compiler prefers the more specific receiver when the bound holds. Otherwise the argument's
`ArgDoc` has `unverified_extractor` set. The strict build rejects the operation. The same
fallback keeps a handler using an unregistered extractor compiling.

The builder clears the body marker when the route validates and the marker reports
`body_verified()`; an unverified body keeps `x-roundhouse-unverified-body`.

## Responses

A response type documents itself through `roundhouse::doc::DocumentedResponse`:

```rust
pub trait DocumentedResponse {
    fn responses(context: &mut dyn SchemaContext) -> Vec<ResponseDoc>;
}
```

The impl owns the status, content type, body schema and headers. Built-ins are ordinary impls:

| Return type | Documented response |
|---|---|
| no `->`, `()` | `200`, empty |
| `Json<T>`, `Html<T>`, `String`, `&str`, `Vec<u8>`, `Bytes`, `Body`, `Attachment<T>`, `File`, `Sse` | `200` with the type's content type |
| `Created<T>` | `201` |
| `NoContent` | `204` |
| `StatusCode`, `(StatusCode, T)`, `Redirect` | `default` |
| `Option<T>`, `Infallible`, `Response` | none |
| `Result<T, E>` | `T`'s responses plus `E`'s |
| `Problem` | `default`, problem+json |

A custom response type implements the trait once and is documented exactly like a built-in:

```rust
pub struct Csv;

impl roundhouse::doc::DocumentedResponse for Csv {
    fn responses(context: &mut dyn SchemaContext) -> Vec<ResponseDoc> {
        vec![ResponseDoc {
            status: 200,
            description: "CSV export".to_string(),
            content_type: Some("text/csv".to_string()),
            schema: Some(roundhouse::doc::schema::string()),
            headers: Vec::new(),
        }]
    }
}
```

`#[handler]` probes the declared return type. If it implements `DocumentedResponse`, the impl
runs. If it does not, the handler still compiles; the strict build reports the missing success.
The macro never assigns a status from a type name.

`impl IntoResponse` has no nameable concrete type, so the macro cannot probe it. A handler with
that return type needs an explicit declaration:

```rust
#[handler(response(200, Json<Note>), response(404, Problem))]
pub async fn show(...) -> impl IntoResponse { ... }
```

`response(status, Type)` calls `Type::responses(..)` and overrides only the status; a bare
`response(status)` is status-only. A typed declaration that contradicts the return type's shape
needs `override_response(..)`.

`Problem` documents `default`. For exact error codes, use `response(404, Problem)` or a typed
error enum that implements `DocumentedResponse` with its own statuses.

Response prose precedence:

1. Handler `@response <status>: text`.
2. `api! response_defaults`.
3. Body type `ApiSchema::description()`.
4. Typed `response_description(status, ..)`.
5. Canonical HTTP reason.

`ApiResponse`/`ApiError` and their derives were removed in 0.4. `Json<T>` needs `T: ApiSchema` to
publish a body schema; a custom response type implements `DocumentedResponse`.

## `ApiSchema` vs `ToSchema`

The schema engine currently uses utoipa internally. `ApiSchema` is the roundhouse adapter:

- it registers the type as a named component (`$ref`);
- it applies roundhouse-only patches (`unique_items`, the `url` → `uri` format mapping);
- it carries `validate_with` hooks (`validate_at`) that survive without `contract`;
- it exposes the type's `#[roundhouse(description = "…")]` or `@description:` through
  `description()`, used for response prose;
- it is the bound automatic body and JSON response documentation requires.

`#[roundhouse::schema]` is the one-annotation form. With `contract` it injects the schema derive
and `ApiSchema`; without `contract` it keeps the runtime `ApiSchema`/`ValidateHook` impls and
drops the utoipa tokens before name resolution.

A type that only implements utoipa's `ToSchema` can still be documented explicitly:

- wrap it in `Json<T>` only if it also implements `ApiSchema`;
- implement `DocumentedResponse` for it and return it, or declare the response with
  `#[handler(response(status, Type))]` and a `DocumentedResponse` impl;
- use a `doc = |docs| ..` hook for a one-off response body;
- `roundhouse::interop::impl_from_utoipa!(Type);` implements the `ApiSchema` adapter for
  generated types.

`Json<T>`'s response impl requires `T: ApiSchema`; a plain `ToSchema` type is not automatically
documented. A blanket `impl<T: ToSchema> ApiSchema for T` would overlap the derive and primitive
implementations.

Component names are the Rust type name by default. Two different Rust types that register the same
name are a `BuildError::ComponentCollision`; `#[roundhouse(name = "module.Name")]` disambiguates
them. The document uses the dotted form (`module.Name`).

## Building the operation

`doc::build` walks the resolved routes in order:

1. **Skip hidden routes.** A hidden route is served but omitted; the document is marked
   `x-roundhouse-hidden`.
2. **Omit `any`.** An `any` method set cannot be one operation; a diagnostic is recorded.
3. **Compute `OperationDoc`.** The marker's statements run, the route's validation policy is
   applied to the body marker, and the entry's `doc` hook runs.
4. **Merge layer docs.** Parameters, body, responses, auth and schemes from module/global
   `LayerDoc`s are added. A layer body only fills an absent body.
5. **Merge guards.** Security guards installed by construction become requirements even if the
   handler did not mention them. A handler's scoped `Auth<A, Scopes>` wins over a bare guard for
   the same scheme. A guard turns `Option<Auth<A>>` into a required scheme while keeping the
   handler's scopes.
6. **Merge parameters.** Parameters are deduplicated by name and location; two schemas for the
   same parameter are `BuildError::ConflictingParameter`.
7. **Fill captures.** Every `{capture}` gets a required path parameter. A scalar `Path<T>` can
   supply the schema when the template has one capture; otherwise a string fallback is used with
   a diagnostic. A path parameter with no capture is `BuildError::UnknownPathParameter`.
8. **Merge responses.** The return type's `DocumentedResponse` output, declared responses,
   extractor failures and layer responses are merged by status. Identical shapes merge their
   headers. Two different 4xx/5xx shapes collapse to a `Problem`, because that is what every
   failure path produces. Two different success bodies keep the first and emit a diagnostic.
9. **Apply typed response declarations.** Declarations add statuses or refine documented ones. A
   bare `status` declares the status as a success and keeps an already-documented response for
   that status. A typed declaration that replaces a different shape without
   `override_response(..)` is `BuildError::ConflictingResponse`; with the override the operation
   is marked `x-roundhouse-overridden-response`. `response_description(..)` replaces the prose of
   an existing status; a description for an undocumented status is a diagnostic.
10. **Require a success.** An operation with no `default` and no 2xx/3xx response is
    `BuildError::UndeclaredSuccess`.
11. **Build security.** Requirements are ANDed in declaration order. `Option<Auth<A>>` adds the
    unauthenticated alternative. Every scheme name must have a registered kind, or the build fails
    with `UnverifiedSecurity`.
12. **Attach extensions** and finish the operation.

The finished document is validated by `validate_document`. The same build records request plans
and the response table in `contract.json`; the runtime compiles the request plans rather than the
document. See [Validation](validation.md).

## Rejection responses

By default (`DocumentRejections::Auto`), every extractor publishes the failures it can produce:

| Extractor | Responses |
|---|---|
| `Json<T>`, `Form<T>` | `400`, `415` |
| `Path<T>`, `Query<T>` | `400` |
| `Auth<A>` | `A::UNAUTHENTICATED`, plus `A::FORBIDDEN` when configured |
| `Extension<T>` via `Strict` | `500` |
| `Multipart<F>` | `400`, `413`, `415` |

`App::document_rejections(false)` publishes only the responses the handler and declarations
supply and marks operations with `x-roundhouse-rejections: none`. This is useful when a gateway
owns the error contract.

## Extensions

Roundhouse adds a small set of `x-roundhouse-*` keys rather than inventing response codes:

| Extension | Meaning |
|---|---|
| `x-roundhouse-hidden` | The document omits at least one route |
| `x-roundhouse-merged` | A hand-written router was merged and is not documented |
| `x-roundhouse-validation: false` | The route opted out of constraint validation |
| `x-roundhouse-body-validation: false` | The route kept parts validation and opted the body out |
| `x-roundhouse-rejections: none` | Extractor rejection responses are not published |
| `x-roundhouse-unverified-body` | The body comes from an extractor whose schema could not be verified |
| `x-roundhouse-unverified-response` | A permissive build published a `default` placeholder for a missing success |
| `x-roundhouse-unverified-extractor` | An argument's documentation could not be resolved |
| `x-roundhouse-overridden-response` | An `override_response(..)` declaration replaced the return type's shape |

## The document artifact

`openapi.json` is OpenAPI 3.1. The runtime serves it verbatim. `Built::openapi_30()` produces a
best-effort 3.0.3 shape by rewriting `type: [T, "null"]`, numeric
`exclusiveMinimum`/`exclusiveMaximum`, nullable `oneOf`, `const` and `examples`. It covers the
constructs this crate emits; it is not a general 3.1 → 3.0 converter.

Two tests keep the artifact honest:

- `tests/openapi.golden.json` is compared against the spine test's document. Regenerate it with
  `ROUNDHOUSE_BLESS=1 cargo test -p roundhouse --test spine openapi_golden` after an intentional
  change.
- `doc::validate_document` runs on every contract build, including after `Contract::document(..)`
  hooks, so a hook cannot publish a path that contradicts its own parameters.

`Built::document()` is a `contract`-only convenience that parses the embedded artifact lazily.
A production `contract-runtime` build should use `Built::openapi_json()` or
`Built::routes()` instead.

## Constraints

- **Automatic body docs require `ApiSchema`; automatic response docs require
  `DocumentedResponse`.** `ToSchema` alone is an explicit declaration, not automatic.
- **No parallel extractor types.** The traits are implemented for axum's types; a custom extractor
  is an impl, not a conversion.
- **No second document model.** The document is utoipa's model behind a thin facade. Roundhouse
  patches schemas and owns assembly, but does not define an alternative OpenAPI type.
- **Unrepresentable routes are omitted, not guessed.** `any` routes are served and excluded.
  Merged routers are served and marked. The document never claims to describe them.
- **Production does not assemble documents.** A `contract-runtime` build has no `DocSource`
  execution and no schema derivation for the document.

## Future

- More extractors can gain `ExtractArg`/`ExtractDoc` impls upstream without a macro change.
- A `#[derive(DocumentedResponse)]` for response enums could remove the hand-written impl for
  multi-status types, but the trait is already the public seam.
- Observation of real traffic can grow richer than the current contract response table.
