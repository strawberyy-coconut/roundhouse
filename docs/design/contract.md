# The build-time contract

**Status: implemented for 0.4.** This note describes the contract compiler as it exists in the
tree. `MIGRATING-0.4.md` is the user-facing guide; the rework plan records the design history.

## Shape

```text
routes! + #[handler] + #[roundhouse::schema] + DocumentedResponse impls
        │
        ├─ build.rs                              generated by `cargo roundhouse init`
        │     calls roundhouse_cli::prepare() before rustc reads include_contract!
        │
        ├─ target/roundhouse/harness              generated per prepare/check
        │     calls <crate>::__roundhouse_contract() from api!
        │
        ├─ cargo roundhouse prepare
        │     one strict build
        │
        ▼
  .roundhouse/contract.json      runtime: operations, request plans, response table, $defs
  .roundhouse/openapi.json       docs: OpenAPI 3.1 projection
        │
        ▼
  contract-runtime               ContractBundle, request validation, verify, verbatim serving
```

`contract.json` is the runtime artifact. `openapi.json` is the documentation artifact. They are
siblings written by one `prepare` run and committed together.

## Build modes

| Mode | Who runs it | What it does |
|---|---|---|
| Automatic | generated `build.rs` | calls `roundhouse_cli::prepare()` when source or manifest inputs change |
| Explicit | `cargo roundhouse prepare` | the same generation on demand |
| Verify | `cargo roundhouse check` | regenerates into `target/roundhouse-check-*` and compares the committed files |

The build script and the CLI share the `roundhouse-cli` library, so there is one implementation.
The generated script skips while the harness compiles the application (the harness sets
`ROUNDHOUSE_BUILDING_CONTRACT`) and skips in CI unless `ROUNDHOUSE_AUTO_CONTRACT=1`. That keeps
`cargo roundhouse check` meaningful: CI builds the committed artifact and the check detects drift.

There is one build, and it is strict. A handler with no documented success response fails
`prepare`; the error points to the handler. There is no discovery pass and no source inference.

The CLI writes only `.roundhouse/` and temporary directories under `target/`. The application's
`src/` and `Cargo.toml` are untouched after `init`.

## Artifact shape

`contract.json` contains:

- `kind` and `contract_version` — the only layout the runtime accepts;
- `generator_version` — informational, from the roundhouse version;
- `operations` — path, method, operation id, handler/source location, security, validation policy
  and the response table. A response is the type's documented response, an extractor/layer
  response or an explicit declaration; there is no inferred provenance;
- `validation` — request body/parts plans and the shared `$defs`;
- `diagnostics` and `openapi` metadata.

`openapi.json` is the OpenAPI 3.1 projection of the same build. It is what the runtime serves.

## Features

| Feature | Adds | utoipa |
|---|---|---|
| `contract-runtime` | `ContractBundle`, `include_contract!`, `App::contract`, `contract.json` request validation, `App::verify_responses`, static docs/`openapi.json` serving | no |
| `contract` | Schema derivation, the document builder, `DocumentedResponse` documentation, `App::openapi`, `App::document` hooks, `roundhouse::openapi`/`interop` (implies `contract-runtime`) | yes |

`roundhouse-cli` is both a library and the binary. `init` adds it as a build-dependency and
generates a `build.rs` that calls `roundhouse_cli::prepare()`; the build script skips while the
harness is compiling (a guard environment variable) and skips in CI unless
`ROUNDHOUSE_AUTO_CONTRACT=1`, so `cargo roundhouse check` still compares the committed artifact.
The harness depends on the application crate and on `roundhouse` with the `contract` feature.
Feature unification makes the application's `api!` block visible for that build only, and its
target directory is `target/roundhouse`. Nothing outside `target/` and `.roundhouse/` is written,
so there is no generated bin and no generated feature. A production application depends on
`roundhouse` with `contract-runtime` only.

## Authoring surface

```rust
roundhouse::api! {
    state = AppState,
    title = "Notes API",
    version = env!("CARGO_PKG_VERSION"),
    root = routes::MODULE,
    servers = ["https://api.example.com"],
    register = [PrivateResponseBody],
    response_defaults = {
        401 => "Authentication is required.",
        500 => "An unexpected server error occurred.",
    },
}
```

`api!` is a proc macro. It validates the option names and generates
`__roundhouse_contract() -> Contract<State>`; without `contract` the function is compiled out.
`register` covers private response or request bodies the harness cannot otherwise name;
`response_defaults` supplies shared prose.

A named return type is documented by its own trait impl:

```rust
#[handler(response(404, Problem))]
pub async fn show(
    State(app): State<AppState>,
    Path(NoteId { id }): Path<NoteId>,
) -> Result<Json<Note>, Problem> {
    match app.get(id) {
        Some(note) => Ok(Json(note)),
        None => Err(Problem::not_found("Note not found")),
    }
}
```

`Json<Note>` documents `200 application/json`; `Problem` documents `default`;
`response(404, Problem)` adds the exact 404 status while keeping the problem body.

## Responses

`roundhouse::doc::DocumentedResponse` is the only source of response documentation:

```rust
pub trait DocumentedResponse {
    fn responses(context: &mut dyn SchemaContext) -> Vec<ResponseDoc>;
}
```

- `Json<T>`, `Html<T>`, `String`, `&str`, `Bytes`, `Body`, `Vec<u8>`, `StatusCode`, `()`,
  `Option<T>`, `Infallible`, `Result<T, E>`, `(StatusCode, T)`, `Attachment<T>`, `File`, `Sse`,
  `Created<T>`, `NoContent`, `Problem`, `Response` and `Redirect` are ordinary impls.
- A custom response type implements the trait once and is documented exactly like a built-in.
- `response(status, Type)` calls `Type::responses(..)` and overrides only the status. A bare
  `response(status)` is status-only.
- `Problem` documents `default`. `response(404, Problem)` or a typed error enum supplies exact
  codes.
- `impl IntoResponse` cannot be named by the macro. If the handler has declarations, those
  document it; otherwise the operation has no documented success and the strict build fails with a
  fix suggestion.
- A declared response that contradicts the return type needs `override_response(..)`. `doc` stays
  available for metadata the declarations cannot express.

`#[handler]` emits a probe for the declared return type. When the type implements
`DocumentedResponse`, the probe calls it. When it does not, the handler still compiles and the
strict build reports the missing success; the macro never guesses by name.

## Contract versioning

`contract.json` starts with `kind`, `contract_version` and `generator_version`.
`contract_version` is the compatibility contract: this runtime accepts only version `1` and fails
`App::build` with `BuildError::InvalidContract` otherwise. A breaking layout change bumps the
version and requires rerunning `cargo roundhouse prepare`. `generator_version` is informational.

## Prose

`/// @response 200: text` and `@summary`/`@description` tags are read by `#[handler]`. Precedence:

1. Handler `@response`.
2. `api! response_defaults` (only when the response still has its canonical description).
3. Body type description.
4. Literal `Problem` title.
5. Canonical HTTP reason.

`@response default:` targets OpenAPI's `default` response.

## Runtime

```rust
const CONTRACT: roundhouse::ContractBundle = roundhouse::include_contract!();

roundhouse::app!(AppState, routes)
    .contract(CONTRACT)
    .openapi_route("/openapi.json")
    .serve("0.0.0.0:3000")
    .await?;
```

- `contract.json` compiles one `$defs` table and per-operation request plans. The raw JSON body
  middleware and the extractor shim use operation id / stable type name, never `TypeId`.
- `openapi_route` serves the committed string verbatim. `App::docs`/`App::swagger` install the
  static UI over that route.
- `Validation::Schema` without a contract fails the build with `MissingContract`; use
  `App::validation(Validation::Off)` for a router-only build.
- `Built::document()` parses the artifact lazily, so a production build does not pay for a typed
  view it never reads.

## Verification

```rust
let built = roundhouse::app!(AppState, routes)
    .contract(roundhouse::include_contract!())
    .verify_responses()
    .build();
```

`verify_responses` checks actual status, content type and JSON body against the response table
keyed by `(method, matched path)`. `cargo roundhouse verify` runs `cargo test` with
`ROUNDHOUSE_VERIFY=1`, which enables the same middleware without a code change. A mismatch is a
`500 Problem` naming the operation and the violated schema.

## CLI

```sh
cargo roundhouse init [--no-build-script]  # .roundhouse/, build.rs and api! snippet
cargo roundhouse prepare              # one strict build
cargo roundhouse check                # CI: artifacts are current
cargo roundhouse explain "GET /v1/notes/{id}"
cargo roundhouse verify [-- args…]    # cargo test with response verification
cargo roundhouse diff [--against <contract.json>] [--check]
```

`explain` prints each response with status, content type, schema ref and description.

## Trait split

- Runtime: `ExtractArg`, `ValidateHook`, `Params`, `MultipartForm`.
- Contract-only: `DocumentedResponse`, `ExtractDoc`, `ParamsDoc`, `MultipartDoc`, `ApiSchema`,
  `DocSource`, schema probes.
- `ApiResponse`/`ApiError` and their derives are removed. Built-in and custom responses use the
  public `DocumentedResponse` trait, or an explicit `#[handler(response(..))]` declaration.

## Implementation notes

- `App::build` without a bundle builds a contract in-process under `contract`; there is no
  separate runtime document assembly and no `TypeId` body/parts map. The schema engine is always
  contract-backed.
- `DocSource` and the response probe still exist under `contract`; they are compiled out of
  production.
- The semantic analyzer is gone. Response documentation comes from the return type's trait impl or
  an explicit declaration.
- `diff` and the OpenAPI 3.0 projection are implemented. Client generation is not part of 0.4.
